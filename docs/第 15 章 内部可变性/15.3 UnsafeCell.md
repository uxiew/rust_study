# 15.3 UnsafeCell

接下来，我们来分析 Cell、RefCell 的实现原理。我们先来考虑两个问题，标准库中的 Cell 类型是怎样实现的？假如让我们自己来实现一遍，是否可行呢？

模仿标准库中的 Cell 类型的公开方法（只考虑最简单的 new、get、set 这三个方法），我们先来一个最简单的版本 V1：

预期编译错误：（E0594）共享引用不能为普通字段赋值。

```rust,compile_fail,no_run
struct CellV1<T> {
    value: T
}

impl<T> CellV1<T> {

    fn new(v: T) -> Self where T: Copy {
        CellV1 { value: v}
    }

    fn set(&self, v: T) {
        self.value = v;
    }

    fn get(&self) -> T where T: Copy {
        self.value
    }
}
```

包装器的 `get` 只对 `Copy` 类型可用，这没有问题。问题在于 `set` 接收 `&self` 却试图直接修改普通字段。

## 第二次尝试：强制转换不授予写权限

预期编译错误：`invalid_reference_casting` 拒绝通过普通共享引用派生的指针写值。即使某种写法绕过了这个诊断，写入仍是未定义行为。

```rust,compile_fail,no_run
struct CellV2<T> {
    value: T,
}

impl<T: Copy> CellV2<T> {
    fn set(&self, value: T) {
        // 反例：普通共享引用派生的指针不允许这样写。
        let raw = &self.value as *const T as *mut T;
        unsafe { *raw = value };
    }
}

fn main() {
    CellV2 { value: 1 }.set(2);
}
```

如果把普通字段假装成可通过共享引用修改的槽位，还会遇到另一层问题：普通包装器可能对 `T` 协变，但可写入的槽位需要 `T` 不变。假如可以把长寿命的槽位临时当成短寿命的槽位，再将短寿命引用写进去，原持有者之后就可能读到悬空引用。

跟着原文的 `Table` 例子逐步看，暂时假设这个写入可以成立：

1. 调用者在 `Table<'long>` 中放入一个能活过多次调用的引用。
2. 辅助函数接收一个短命局部变量。如果 `Table` 对内容协变，就能把同一个表当作 `Table<'short>` 借用。
3. 通过这个短期视图写入局部变量的引用，改动的仍是原表里的那个槽。
4. 辅助函数返回，局部变量销毁；原表的类型却没有变，仍宣称槽里的引用可用于 `'long`。

只读容器允许这种借用收缩，因为缩短后只能读；可写槽位则不能同时向外承诺长引用、向内接收短引用。问题不在某个运行结果，而在调用方可完全用安全代码破坏封装承诺的不变量。

用真正的 `Cell` 检验这一推导。预期编译错误：`Cell<T>` 对 `T` 不变，不能把内部的引用生命周期从 `'long` 缩成 `'short`。

```rust,compile_fail,no_run
use std::cell::Cell;

struct Table<'a> {
    cell: Cell<&'a isize>,
}

fn shorten<'long: 'short, 'short>(table: &Table<'long>, value: &'short isize) {
    let shorter: &Table<'short> = table;
    shorter.cell.set(value);
}

fn main() {}
```

## 第三次尝试：使用 `UnsafeCell`

`UnsafeCell<T>` 是内部可变性的原语，是编译器识别的语言项。下面是内部定义的简化摘录，不是用户可复制的实现：

```text
#[lang = "unsafe_cell"]
pub struct UnsafeCell<T: ?Sized> {
    value: T,
}
```

请注意这个类型上面的标记 `#[lang=...]`。这个标记意味着这个类型是个特殊类型，是被编译器特别照顾的类型。这个类型的说明文档需要特别提示读一下：

```text
The core primitive for interior mutability in Rust.

UnsafeCell allows mutation through a shared reference to the cell; it does not relax the uniqueness guarantee of mutable references.

Types like Cell<T> and RefCell<T> use this type to wrap their internal data.
```

`UnsafeCell::get` 返回裸指针；调用者仍需保证对齐、有效性、独占引用及没有数据竞争。它只改变包裹数据的共享不可变性，不会让普通的 `&T` 获得写权限。

`Cell` 和 `RefCell` 都使用这个原语，但一个复制或替换值，另一个用守卫跟踪动态借用。这也解释了为什么内部可变性有语言层支持，而大多数用户只需要使用安全库类型。

可以把检查分成两层：运行时，任何裸指针访问都要遵守当前借用状态；类型层面，`UnsafeCell<T>` 对 `T` 不变，阻止了刚才那次转换。单独给一个字段加 `unsafe` 块既不能改变它的型变，也不能为共享引用增加权限。

使用标准库 `Cell` 时，类型边界也反映了取值方式。`get` 只能按值返回一个 `Copy` 值，`replace` 则接受新值、返回旧值，不必复制：

| 操作 | 为什么安全 |
| --- | --- |
| `Cell::get` | 返回一份副本，不保留内部数据的引用。 |
| `Cell::replace` | 交出旧值的所有权，不让调用方继续持有旧槽位的访问权。 |
| `Cell::get_mut` | 要求先有 `&mut Cell<T>`，此时才能直接借出内部值。 |

下面用不返回内部引用、不能跨线程共享的 `u32` 包装器收尾：

```rust
use std::cell::UnsafeCell;

struct Counter(UnsafeCell<u32>);

impl Counter {
    fn set(&self, n: u32) {
        // SAFETY: Counter 不是 Sync，也不暴露内部引用或指针。
        unsafe { self.0.get().write(n) };
    }

    fn get(&self) -> u32 {
        // SAFETY: 指针指向已初始化的 u32；没有并发修改。
        unsafe { self.0.get().read() }
    }
}

fn main() {
    let counter = Counter(UnsafeCell::new(0));
    let shared = &counter;
    shared.set(1);
    assert_eq!(counter.get(), 1);
}
```
