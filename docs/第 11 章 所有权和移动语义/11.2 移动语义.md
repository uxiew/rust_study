# 11.2 移动语义

一个变量可以把它拥有的值转移给另外一个变量，称为“所有权转移”。赋值语句、函数调用、函数返回等，都有可能导致所有权转移。

比如：

```rust
fn create() -> String {
    let s = String::from("hello");
    return s; // 所有权转移，从函数内部移动到外部
}

fn consume(s: String) { // 所有权转移，从函数外部移动到内部
    println!("{}", s);
}

fn main() {
    let s = create();
    consume(s);
}
```

在上面这个例子中，函数参数和返回值都发生了所有权转移：

所有权转移的步骤分解如下。

1）`main`函数调用`create`函数。

2）`create` 创建字符串。可以把局部变量 `s` 理解为管理一个堆上的字符缓冲区，不要求 `String` 本身实际放在栈上。

3）`create` 返回时把 `s` 的所有权移给调用方，不克隆堆上的字符。

```mermaid
flowchart LR
    A["create 创建 String"] -->|"返回：移动"| B["main 中的 s"]
    B -->|"传参：移动"| C["consume 中的 s"]
    C -->|"函数返回"| D["析构 String，释放缓冲区"]
```

4）`main` 调用 `consume` 时，再把它拥有的字符串移动给形参。

5）当`consume`函数结束的时候，它并没有把内部的局部变量再转移出来，这种情况下，`consume`内部局部变量的生命周期就该结束了。
这个局部变量`s`生命周期结束的时候，会自动释放它所拥有的内存，因此字符串也就被释放了。

非 `Copy` 的值按值使用时默认被移动，被移空的位置在重新初始化之前不能使用。
比如向函数传递参数会将所有权转移到函数的参数上，从函数返回值会将所有权转移到调用者身上，创建一个元组会将值转移到元组中等等。

Rust 的这一规定非常有利于编译器静态检查。
Rust 的移动本身不会调用用户自定义的移动构造函数。赋值给已初始化的位置仍可能析构旧值。
在 C++ 里面，`std::vector<int> v1 = v2;`是复制语义，而 Rust 里面的`let v1: Vec<i32> = v2;`是移动语义。
如果要在 Rust 里面实现复制语义，需要显式写出函数调用`let v1: Vec<i32> = v2.clone();`。
C++ 中用移动构造或移动赋值完成同类操作；这些操作可以由编译器生成，也可以由类型自己定义。

对于“移动语义”，最后还需要强调的一点是，“语义”不代表最终的执行效率。
“语义”只是规定了什么样的代码是编译器可以接受的，以及它执行后的效果可以用怎样的思维模型去理解。
编译器有权在不改变语义的情况下做任何有利于执行效率的优化。语义和优化是两个阶段的事情。
我们可以把移动语义想象成执行了一个`memcpy`，但真实的汇编代码未必如此。

比如：

```text
fn create() -> BigObject {
    let local = …;
    return local;
}
let v = create();
```

完全可能被优化为类似如下的效果：

```text
caller: reserve return slot for BigObject
callee: initialize the slot directly
caller: use the now-initialized value
```

编译器可以提前在调用方为大对象预留空间，再让被调用者直接初始化结果槽；这个模型并不构造指向未初始化值的 Rust 引用。
这样就避免了大对象的复制工作，参数传递只是一个指针而已。
这么做是完全满足移动语义要求的，而且编译器还有权利做更多类似的优化。
