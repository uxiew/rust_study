# 18.3 Panic Safety

C++中引入了“异常”这个机制之后，同时也带入了一个“异常安全”（exception safety）的概念。对这个概念不熟悉的读者，建议阅读以下文档：

<http://www.stroustrup.com/except.pdf>

异常安全存在四种层次的保证：

* No-throw——操作不会把异常传播给调用方。

* Strong exception safety——强异常安全保证可以保证异常发生的时候，所有的状态都可以“回滚”到初始状态，不会导致状态不一致的问题；

* Basic exception safety——异常后依然满足类型不变量，不泄漏本应释放的资源；业务结果可能已改变。

* No exception safety——没有任何异常安全保证。

当我们在系统中使用了“异常”的时候，就一定要想清楚，每个组件应该提供哪种层级的异常安全保证。在 Rust 中，这个问题同样存在，但是一般叫作 panic safety，与“异常”说的是同一件事情。

[Rust 1.100.0 的 `Box<[T], A>::clone`](https://doc.rust-lang.org/1.100.0/src/alloc/boxed.rs.html#2195) 先克隆分配器，再把工作委托给 `to_vec_in`，最后把结果转换回装箱切片：

```text
impl<T: Clone, A: Allocator + Clone> Clone for Box<[T], A> {
    fn clone(&self) -> Self {
        let alloc = Box::allocator(self).clone();
        self.to_vec_in(alloc).into_boxed_slice()
    }
    …
}
```

顺着这条调用链理解原书的推导。以 `Box<[T]>` 为例，要分配一块新缓冲区，再逐一克隆源切片。Rust 1.100 的具体实现已经演化；以下是说明不变量的模型，不是标准库的逐字拷贝。

```text
allocate a buffer for n values
initialized = 0
for each element:
    clone the element          // this may panic
    write the clone at initialized
    initialized += 1

if completed:
    hand the entire initialized buffer to Box
on unwind:
    drop only initialized values, then free the buffer
```

为什么不用先设置长度，再循环填充呢？`T::clone` 是用户可定义的操作，可能在任意元素上 panic。提前设置长度会让析构将未初始化的槽位当作 `T`；直到最后才记录长度，则可能丢掉前面已经成功创建的值。

可以利用 RAII：让缓冲区或守卫记录已初始化的前缀。若克隆中途展开，守卫析构它已经接管的值。用安全接口可直接把这一责任交给 `Vec`：

```rust
fn clone_box<T: Clone>(values: &[T]) -> Box<[T]> {
    let mut cloned = Vec::with_capacity(values.len());
    for x in values {
        cloned.push(x.clone());
    }
    cloned.into_boxed_slice()
}

fn main() {
    assert_eq!(&*clone_box(&[String::from("rust")]), ["rust"]);
}
```

大家可以去翻一下标准库中的代码，有大量类似的模式存在，都是因为需要考虑 panic safety 问题。Rust 的标准库在编写的时候有这样一个目标：即便发生了 panic，也不会产生“内存不安全”和“线程不安全”的情况。

在 Rust 中，什么情况下 panic 会导致 bug 呢？这种情况的产生需要两个条件：

* panic 导致了数据结构内部的状态错误；

* 这个错误的状态会在以后被观测到。

在 unsafe 代码中，这种情况非常容易出现。所以，在写 unsafe 代码的时候，需要对这种情况非常敏感小心，一不小心就可能因为这个原因制造出“内存不安全”。

安全代码不会因此产生未定义行为，但业务状态仍可能只更新了一半。考虑如下例子：

---

预期编译错误：（E0277）闭包捕获了 `&mut Vec<_>`，不满足 `UnwindSafe`。

```rust,compile_fail,no_run
use std::panic;

fn main() {
    let mut x : Vec<i32> = vec![1];
    let mut y : Vec<i32> = vec![2];
    panic::catch_unwind(|| {
        x.push(10);
        panic!("user panic");
        y.push(100);
    }).ok();

    println!("Observe partially updated data: {:?} {:?}", x, y);
}
```

---

这里我们必须使用 catch\_unwind 来阻止栈展开，否则这两个数据结构就一起被销毁了，无法观测到 panic 引发的错误状态。编译可见，这段代码是无法编译通过的，错误如下：

---

```text
error[E0277]: the trait bound `&mut std::vec::Vec<i32>: std::panic::UnwindSafe` is not satisfied
```

---

这是什么原因呢？因为 catch\_unwind 的签名是这样的：

---

```text
pub fn catch_unwind<F: FnOnce() -> R + UnwindSafe, R>(f: F) -> Result<R>
```

---

它要求闭包参数满足 UnwindSafe 条件，而标准库中早就标记好了&mut 型指针是不满足 UnwindSafe trait 的。有些类型，天生就不适合在 catch\_unwind 的外部和内部同时存在。

有了这个约束条件，被 panic 破坏掉的数据结构被外部继续观测、使用的几率就小了许多。

当然，编译器是永远不知道用户的真实意图的，可能在某些场景下，用户就是要这样写，而且不认为这些数据结构是“被破坏”的状态。怎么修复上面这个编译错误呢？示例如下：

---

```rust
use std::panic;
use std::panic::AssertUnwindSafe;

fn main() {
    let mut x : Vec<i32> = vec![1];
    let mut y : Vec<i32> = vec![2];
    panic::catch_unwind(AssertUnwindSafe(|| {
        x.push(10);
        panic!("user panic");
        y.push(100);
    })).ok();

    println!("Observe partially updated data: {:?} {:?}", x, y);
}
```

---

`AssertUnwindSafe` 断言调用者已考虑中断后的状态，不会回滚修改，也不能用它证明 `unsafe` 正确。可以缩小断言范围，例如只包装已经检查过的捕获值。

同理，在多线程情况下也有类似的问题。比如，我们把第 29 章经常用的示例的多线程修改全局变量的程序改改，在其中某个线程中制造一个 panic：

---

```rust
use std::sync::Arc;
use std::sync::Mutex;
use std::thread;

const COUNT: u32 = 1000;

fn main() {
    let global = Arc::new(Mutex::new(0));

    let clone1 = global.clone();
    let thread1 = thread::spawn(move|| {
        for _ in 0..COUNT {
            match clone1.lock(){
                Ok(mut value) => *value +=1,
                Err(poisoned) => {
                    let mut value = poisoned.into_inner();
                    *value += 1;
                }
            }
        }
    });

    let clone2 = global.clone();
    let thread2 = thread::spawn(move|| {
        for _ in 0..COUNT {
            let mut value = clone2.lock().unwrap();
            *value -= 1;
            if *value < 100 {
                println!("make a panic");
                panic!("");
            }
        }
    });

    thread1.join().ok();
    thread2.join().ok();
    println!("final value: {:?}", global);
}
```

---

第二个线程持有锁时 panic，`Mutex` 通常会被标为中毒；随后 `lock` 返回错误。`into_inner` 可以取出守卫，但应检查或修复不变量后再继续。中毒是提示性机制，不能当作 `unsafe` 安全屏障。

不想暴露部分更新，可以先构造完整的新状态，再一次提交：

```rust
fn replace_all<T: Clone>(target: &mut Vec<T>, source: &[T]) {
    let replacement: Vec<T> = source.to_vec();
    *target = replacement;
}

let mut target = vec![1];
replace_all(&mut target, &[2, 3]);
assert_eq!(target, [2, 3]);
```
