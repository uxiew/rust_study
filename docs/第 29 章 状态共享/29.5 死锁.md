# 29.5 死锁

既然 Rust 中提供了“锁”机制，那么 Rust 中是否有可能出现“死锁”的现象呢？我们用经典的“哲学家就餐问题”来演示一下。

问题：假设有 5 个哲学家，共享一张放有 5 把椅子的桌子，每人分得一把椅子，但是，桌子上共有 5 支筷子，在每人两边各放一支，哲学家们在肚子饥饿时才试图分两次从两边拿起筷子就餐。

条件：

* 拿到两支筷子时哲学家才开始吃饭；

* 如果筷子已在他人手上，则该哲学家必须等他人吃完之后才能拿到筷子；

* 任一哲学家在自己未拿到两只筷子前却不放下自己手中的筷子。

代码如下：

```rust,no_run
use std::thread;
use std::sync::{Arc, Barrier, Mutex};

struct Philosopher {
    name: String,
    left: usize,
    right: usize,
}


impl Philosopher {
    fn new(name: &str, left: usize, right: usize) -> Philosopher {
        Philosopher {
            name: name.to_string(),
            left: left,
            right: right,
        }
    }


    fn eat(&self, table: &Table) {
        let _left = table.forks[self.left].lock().unwrap();
        println!("{} take left fork.", self.name);
        table.all_ready.wait();
        let _right = table.forks[self.right].lock().unwrap();
        println!("{} take right fork.", self.name);
        println!("{} is done eating.", self.name);
    }
}

struct Table {
    forks: Vec<Mutex<()>>,
    all_ready: Barrier,
}

fn main() {
    let table = Arc::new(Table { all_ready: Barrier::new(5), forks: vec![
        Mutex::new(()),
        Mutex::new(()),
        Mutex::new(()),
        Mutex::new(()),
        Mutex::new(()),
    ]});

    let philosophers = vec![
        Philosopher::new("Judith Butler", 0, 1),
        Philosopher::new("Gilles Deleuze", 1, 2),
        Philosopher::new("Karl Marx", 2, 3),
        Philosopher::new("Emma Goldman", 3, 4),
        Philosopher::new("Michel Foucault", 4, 0),
    ];

    let handles: Vec<_> = philosophers.into_iter().map(|p| {
        let table = table.clone();

        thread::spawn(move || {
            p.eat(&table);
        })
    }).collect();
    for h in handles {
        h.join().unwrap();
    }
}
```

这段程序用于展示死锁，只编译，不要直接运行。屏障让 5 人都拿起左边的筷子后再尝试拿右边的筷子。于是每个人都等着下一位释放资源，形成循环等待：

```mermaid
flowchart LR
    A["哲学家 0"] --> B["哲学家 1"]
    B --> C["哲学家 2"]
    C --> D["哲学家 3"]
    D --> E["哲学家 4"]
    E --> A
```

一种修复方式是约定所有线程都先拿编号较小的筷子，再拿编号较大的筷子。统一获取锁的顺序可以打破循环等待；Rust 的借用检查本身不会阻止死锁。
