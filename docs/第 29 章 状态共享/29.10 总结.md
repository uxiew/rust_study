
# 29.10 总结

从前面的分析可见，Rust 一方面禁止随意共享可变变量，另一方面提供了安全共享的类型。回到数据竞争的三个条件，可以简单记成：

> Alias + Mutation + No ordering（共享访问 + 修改 + 缺少适当的同步）

这和第二部分的内存安全规则是一脉相承的：同一份数据可以有多个共享读者，而可变借用必须独占。线程之间需要共享写入时，锁能把这些访问排出先后顺序，原子类型则提供专门的访问方式。

## 29.10.1 单线程工具与跨线程工具

1. **Rc 与 Arc。** 两者都有相应的弱指针 `Weak`。Rc 用普通整数计数；Arc 用原子计数，使不同线程可以克隆和丢弃自己的指针。原子计数只保护计数，不代表内部值也适合跨线程共享。
2. **RefCell 与 Mutex / RwLock。** 它们都提供内部可变性。RefCell 在运行时检查借用规则，不提供线程间同步；当 `T: Send` 时，仍能把整个 `RefCell<T>` 交给另一个线程。锁则控制不同线程谁能读写。锁中毒让下一位拿到守卫的线程知道前一位可能在更新中 panic，但不是数据一致性的证明。
3. **Cell 与原子类型。** `Cell` 允许通过共享引用替换值，却不会同步不同线程的访问。标准库的原子类型可以在相应平台上安全地跨线程加载和存储，还提供不可分割的读改写。并非每种 `T` 都有相应的标准库原子类型；需要同时更改若干字段时，常用 `Mutex<T>` 来保护整个操作。

| 需求 | 优先考虑 |
| --- | --- |
| 跨线程共享所有权 | `Arc<T>`；它只同步引用计数 |
| 共享并修改多字段数据 | `Mutex<T>`；如果通常只读，也可考虑 `RwLock<T>` |
| 独立计数器 | 原子整数；用 `fetch_add` 等读改写操作完成更新 |
| 多个线程在同一点会合 | `Barrier` |
| 等待共享状态达到条件 | `Mutex<T>` 与 `Condvar` |
| 每个线程有自己的状态 | `thread_local!` |

## 29.10.2 检查与运行时成本

编译器提供 `Send`、`Sync` 和借用检查等通用机制，线程库用这些约束来定义安全的接口。不需要额外的垃圾回收运行时来做这些类型检查，但锁竞争、原子操作和线程调度本身仍有运行时开销。安全 Rust 防止数据竞争，也不意味着可以忽略死锁、丢失更新一类业务错误。

这种划分允许标准库与第三方库都借助同一套类型规则提供并发抽象，无需编译器为每一个 API 写特殊检查。如果应用只需要把数据交给另一线程处理，下一章介绍的消息管道可能比共享变量更直接。
