
# 29.1 Arc

Arc（Atomic Reference Counted，原子引用计数）是 Rc 的线程安全版本。注意第一个单词是 atomic 而不是 automatic：区别在于 Arc 用原子操作更新引用计数。克隆只增加引用计数，不复制 `T`；最后一个强引用被丢弃时，内部值随之析构。

下面启动多个线程，共享读取同一个 `Vec`：

```rust
use std::{sync::Arc, thread};

fn main() {
    let numbers: Vec<_> = (0..100u32).collect();
    let shared_numbers = Arc::new(numbers);
    let mut workers = Vec::new();

    for _ in 0..10 {
        // 每个子线程拥有一个 Arc，所有 Arc 都指向同一个 Vec。
        let child_numbers = Arc::clone(&shared_numbers);
        workers.push(thread::spawn(move || {
            let local_numbers = &child_numbers[..];
            local_numbers.iter().sum::<u32>()
        }));
    }

    for worker in workers {
        assert_eq!(worker.join().unwrap(), 4950);
    }
    assert_eq!(shared_numbers.len(), 100);
}
```

如果将上面的 `Arc` 改为 `Rc`，编译器会在 `spawn` 处报错：闭包捕获的 `Rc<Vec<u32>>` 不是 `Send`。第 28.1 节给出了同一原因的完整反例。

为什么错误能在编译阶段检查出来？`spawn` 要求闭包是 `Send`；闭包不必自己实现 `Send`，编译器会检查它捕获的数据。本例中，闭包捕获了共享指针，而两种指针的跨线程约束不同。以下为标准库实现的简化摘录，省略了分配器参数：

```text
unsafe impl<T: ?Sized + Sync + Send> Send for Arc<T> {}
unsafe impl<T: ?Sized + Sync + Send> Sync for Arc<T> {}

impl<T: ?Sized> !Send for Rc<T> {}
impl<T: ?Sized> !Sync for Rc<T> {}
```

| 指针类型（默认分配器） | 跨线程条件 |
| --- | --- |
| `Rc<T>` | 既不是 `Send` 也不是 `Sync`；引用计数不是原子的 |
| `Arc<T>` | 当 `T: Send + Sync` 时同时实现 `Send` 和 `Sync` |

具体到上例：`u32` 既是 `Send` 也是 `Sync`，所以 `Vec<u32>` 具备这两个 trait；使用默认分配器的 `Arc<Vec<u32>>` 因此是 `Send`，最终闭包也满足 `spawn` 的要求。若换成 `Arc<Cell<u32>>`，这条推导就在 `Cell<u32>: Sync` 处失败。

Arc 的原子操作保护的是引用计数，不会替内部值同步。如果只在单线程中共享所有权，可以用 Rc 避免原子计数的开销；如果跨线程还需要共同修改数据，可以使用下一节的 `Arc<Mutex<T>>`。
