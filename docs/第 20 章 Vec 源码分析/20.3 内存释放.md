# 20.3 内存释放

## 20.3.1 Vec 的析构函数

在 Rust 中，RAII 手法是非常常用的资源管理方式。Vec 就是利用 RAII 来进行资源管理的。因此，接下来我们需要分析 Vec 的析构函数：

下面是 [Rust 1.100.0 的析构实现](https://doc.rust-lang.org/1.100.0/src/alloc/vec/mod.rs.html#4317)：

```text
const unsafe impl<#[may_dangle] T: [const] Destruct, A: [const] Allocator + [const] Destruct> Drop
    for Vec<T, A>
{
    fn drop(&mut self) {
        // ignore-tidy-undocumented-unsafe
        unsafe {
            // use drop for [T]
            // use a raw slice to refer to the elements of the vector as weakest necessary type;
            // could avoid questions of validity in certain cases
            self.as_mut_ptr().cast_slice(self.len).drop_in_place()
        }
        // RawVec handles deallocation
    }
}
```

这里只构造含前 `len` 个元素的裸切片，因为这部分才含有有效的 `T`。`drop_in_place` 使用编译器生成的析构代码；针对切片，它会析构切片中的元素，不会访问尾部空余槽位。

`Vec::drop` 处理元素，随后字段析构负责释放分配。再看 [`RawVec::drop`](https://doc.rust-lang.org/1.100.0/src/alloc/raw_vec/mod.rs.html#439)：

```text
const unsafe impl<#[may_dangle] T, A: [const] Allocator + [const] Destruct> Drop for RawVec<T, A> {
    /// Frees the memory owned by the `RawVec` *without* trying to drop its contents.
    fn drop(&mut self) {
        // SAFETY: We are in a Drop impl, self.inner will not be used again.
        unsafe { self.inner.deallocate(T::LAYOUT) }
    }
}
```

分配器只需要当前的分配地址和布局，不应再次调用 `T::drop`。`RawVecInner::deallocate` 通过 `current_memory` 取得这两个值：

```text
    unsafe fn deallocate(&mut self, elem_layout: Layout) {
        // SAFETY: Caller ensures `elem_layout` is correct for `self`.
        if let Some((ptr, layout)) = unsafe { self.current_memory(elem_layout) } {
            // SAFETY: `current_memory` gives us a pointer with provenance for our allocation
            // and a matching layout. Caller ensures we're not accessed again after deallocating.
            unsafe {
                self.alloc.deallocate(ptr, layout);
            }
        }
    }
```

`current_memory` 不为尚未分配的状态生成布局；若有实际分配，则按分配时使用的元素布局与容量还原：

```text
    const unsafe fn current_memory(&self, elem_layout: Layout) -> Option<(NonNull<u8>, Layout)> {
        if elem_layout.size() == 0 || self.cap.as_inner() == 0 {
            None
        } else {
            // We could use Layout::array here which ensures the absence of isize and usize overflows
            // and could hypothetically handle differences between stride and size, but this memory
            // has already been allocated so we know it can't overflow and currently Rust does not
            // support such types. So we can do better by skipping some checks and avoid an unwrap.
            // SAFETY: Upheld by caller, unless the element size is 0 which is checked against.
            unsafe {
                let alloc_size = elem_layout.size().unchecked_mul(self.cap.as_inner());
                let layout = Layout::from_size_align_unchecked(alloc_size, elem_layout.align());
                Some((self.ptr.into(), layout))
            }
        }
    }
```

零大小元素与未分配的缓冲区都没有需要释放的内存。即使是零大小类型，其元素也可能实现 `Drop`；是否析构元素和是否归还分配是两件事。

## 20.3.2 Drop Check

`'a: 'b` 表示 `'a` 至少覆盖 `'b`，不是比较两个变量的声明行号。声明先后仍能决定本地绑定的析构顺序。没有用户析构函数的普通引用，只要在被借用的值有效时使用就可以：

```rust
fn main() {
    let (mut a, b): (Option<&i32>, i32) = (None, 1);
    assert_eq!(a, None);
    a = Some(&b);
    assert_eq!(a, Some(&1));
    // 离开作用域时，不会有用户析构函数再去读取 a 中的引用。
}
```

同一条 `let` 语句可以引入多个绑定。但是这些绑定既不同时析构，也不能因此假定彼此可以在析构时相互借用。元组字段与解构产生的局部绑定也不同：

| 写法 | 应看哪条规则 |
| --- | --- |
| 分别声明两个局部绑定 | 同一析构作用域内，局部绑定通常按声明的逆序析构。 |
| 一条语句解构到两个局部绑定 | 仍然有明确的模式绑定析构顺序，见 [Rust Reference](https://doc.rust-lang.org/reference/destructors.html#drop-scopes)。 |
| 一个元组值保持未解构 | 元组字段按字段顺序析构。 |

先验证两个单独声明的绑定的顺序。这个例子把可观察的析构事件存进数组：

```rust
use std::cell::RefCell;

struct Observe<'a>(&'a RefCell<Vec<char>>, char);

impl Drop for Observe<'_> {
    fn drop(&mut self) {
        self.0.borrow_mut().push(self.1);
    }
}

fn main() {
    let order = RefCell::new(Vec::new());
    {
        let _first = Observe(&order, 'a');
        let _second = Observe(&order, 'b');
        assert!(order.borrow().is_empty());
    }
    assert_eq!(order.into_inner(), ['b', 'a']);
}
```

换成可能读取借用的析构函数，检查就不同了：编译器必须考虑它退出作用域时可能再访问那个引用，不允许仅凭最后一条显式语句来结束借用。

预期编译错误：（E0597）`data` 在 `inspect` 之前析构，但 `Inspect::drop` 还会访问它。交换两个绑定的声明顺序即可修复。

```rust,compile_fail,no_run
struct Inspect<'a>(Option<&'a String>);

impl Drop for Inspect<'_> {
    fn drop(&mut self) {
        if let Some(s) = self.0 {
            println!("{s}");
        }
    }
}

fn main() {
    let mut inspect = Inspect(None);
    let data = String::from("rust");
    inspect.0 = Some(&data);
}
```

声明顺序确定后，反过来试一次：先声明被借用的数据，再声明使用它的观察者。在退出内层作用域时，观察者先读取并放弃借用，然后数据才被释放。

```rust
struct Inspect<'a>(&'a str);

impl Drop for Inspect<'_> {
    fn drop(&mut self) {
        assert_eq!(self.0, "rust");
    }
}

fn main() {
    let data = String::from("rust");
    {
        let _inspect = Inspect(&data);
        assert_eq!(data.len(), 4);
    }
    // 观察者已经析构，data 仍然有效。
    assert_eq!(data, "rust");
}
```

Drop Check 根据类型和析构函数接口保守地检查，不承诺从每个 `drop` 的实现体中推断出哪些借用不会被访问。对于标准库这类必须实现容器的代码，才有必要显式表达例外。

标准库的 `Vec` 实现在析构时不会读取已经不再有效的借用，但有人为容器写 `unsafe impl Drop` 时，仍要顾及元素自己的析构逻辑。下面是更小的实验示例：包装器只存借用，不持有需要析构的 `T`，析构时不访问该借用。

需要 Nightly 以及 `dropck_eyepatch` 特性，见 [Rust Unstable Book](https://doc.rust-lang.org/unstable-book/language-features/dropck-eyepatch.html)。稳定应用应调整声明顺序和所有权，不要依赖此属性。

```rust:{channel:"nightly",edition:"2024"}
#![feature(dropck_eyepatch)]

struct NoRead<'a>(Option<&'a String>);

// SAFETY: 析构不会读取或使用 'a 指向的数据。
unsafe impl<#[may_dangle] 'a> Drop for NoRead<'a> {
    fn drop(&mut self) {}
}

fn main() {
    let mut wrapper = NoRead(None);
    let data = String::from("rust");
    wrapper.0 = Some(&data);
}
```

使用该属性时，不能忽略类型实际拥有的元素：如果元素析构仍需使用某些数据，该约束仍须满足。也不要把它作为调整普通局部变量析构顺序的工具。参见 [dropck RFC](https://rust-lang.github.io/rfcs/1327-dropck-param-eyepatch.html)。
