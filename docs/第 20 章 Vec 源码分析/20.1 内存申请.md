# 20.1 内存申请

首先，我们知道 Vec 是一个动态数组，它会根据情况动态扩展当前的空间大小。
在 Rust 以及 C++ 这样的语言中，动态数组这样的类型是由库来实现的，而不是像某些带 GC 的语言一样由运行时环境内置提供。
这是因为 Rust 和 C++ 一样，都具备对内存的直接控制力，其中一个表现就是，可以手动调用内存分配器，自己管理内存分配和释放的策略。

动态数组的基本思想是区分拥有者与缓冲区：`Vec` 管理一个通常位于堆上的缓冲区，容量不足时申请更大的空间。对比之下，`[T; N]` 的元素就保存在数组值本身，数组值也可以放到堆上。

在 [Rust 1.100.0 的源码](https://doc.rust-lang.org/1.100.0/src/alloc/vec/mod.rs.html#442) 中，从 `Vec` 的定义开始看：
它的定义很简单：

```text
pub struct Vec<
    T,
    #[stable(feature = "allocator_api", since = "1.100.0")] A: Allocator = Global,
> {
    buf: RawVec<T, A>,
    len: usize,
}
```

两个字段分工不同：`RawVec<T, A>` 管理分配，`len` 则是当前已初始化的元素数量。容量大于长度不代表多出来的槽位已经含有 `T`。
Vec 的 new 和 capacity 方法都很简单：

```text
    pub const fn new() -> Self {
        Vec { buf: RawVec::new(), len: 0 }
    }

    pub const fn with_capacity(capacity: usize) -> Self {
        Self::with_capacity_in(capacity, Global)
    }

    pub fn with_capacity_in(capacity: usize, alloc: A) -> Self {
        Vec { buf: RawVec::with_capacity_in(capacity, alloc), len: 0 }
    }

    pub const fn new_in(alloc: A) -> Self {
        Vec { buf: RawVec::new_in(alloc), len: 0 }
    }
```

上面几个构造方法不添加元素；继续向下看 [`RawVec`](https://doc.rust-lang.org/1.100.0/src/alloc/raw_vec/mod.rs.html#78)。1.100.0 把依赖 `T` 的部分和只需要内存布局的部分拆开：

```text
pub(crate) struct RawVec<T, A: Allocator = Global> {
    inner: RawVecInner<A>,
    _marker: PhantomData<T>,
}

/// Like a `RawVec`, but only generic over the allocator, not the type.
///
/// As such, all the methods need the layout passed-in as a parameter.
///
/// Having this separation reduces the amount of code we need to monomorphize,
/// as most operations don't need the actual type, just its layout.
#[allow(missing_debug_implementations)]
struct RawVecInner<A: Allocator = Global> {
    ptr: NonNull<u8>,
    /// Never used for ZSTs; it's `capacity()`'s responsibility to return usize::MAX in that case.
    ///
    /// # Safety
    ///
    /// `cap` must be in the `0..=isize::MAX` range.
    cap: Cap,
    alloc: A,
}
```

把元素布局作为参数传给 `RawVecInner<A>`，让底层分配逻辑不必因每一种元素类型重新实例化。

`Vec<T, A>` 和 `RawVec<T, A>` 都带有分配器参数。Rust 1.100.0 稳定了 `Vec::new_in` 和 `Vec::with_capacity_in` 等接口，但不表示分配器扩展接口全部稳定。默认分配器 `Global` 本身是零大小类型；自定义分配器不一定如此。

```rust
fn main() {
    use std::alloc::System;

    let mut values: Vec<u32, System> = Vec::with_capacity_in(4, System);
    assert_eq!(values.len(), 0);
    assert!(values.capacity() >= 4);
    values.push(42);
    assert_eq!(values.as_slice(), &[42]);
    assert_eq!(Vec::<()>::new().capacity(), usize::MAX);
}
```

从 `RawVec<T, A>` 往内转交分配器与布局时，使用了这样的适配层：

```text
    pub(crate) fn with_capacity_in(capacity: usize, alloc: A) -> Self {
        Self {
            inner: RawVecInner::with_capacity_in(capacity, alloc, T::LAYOUT),
            _marker: PhantomData,
        }
    }

    pub(crate) const fn new_in(alloc: A) -> Self {
        // Check assumption made in `current_memory`
        const { assert!(T::LAYOUT.size() % T::LAYOUT.align() == 0) };
        Self { inner: RawVecInner::new_in(alloc, Alignment::of::<T>()), _marker: PhantomData }
    }
```

不预分配时，调用链最终会走到 `RawVecInner::new_in`：

```text
    const fn new_in(alloc: A, align: Alignment) -> Self {
        let ptr = NonNull::without_provenance(align.as_nonzero_usize());
        // `cap: 0` means "unallocated". zero-sized types are ignored.
        Self { ptr, cap: ZERO_CAP, alloc }
    }
```

`ptr` 是满足对齐的非空占位指针，不是可解引用的元素地址。内部零容量在这里表示尚未分配；如果 `T` 是零大小类型，对外报告的容量为 `usize::MAX`。

长度、实际存储的容量字段与对外容量是三件事。对于非零大小元素，容量直接来自分配；零大小元素从这里得到特殊值：

```text
    pub(crate) const fn capacity(&self) -> usize {
        self.inner.capacity(size_of::<T>())
    }

    const fn capacity(&self, elem_size: usize) -> usize {
        if elem_size == 0 { usize::MAX } else { self.cap.as_inner() }
    }
```

带容量的构造继续调用 `try_allocate_in`。下面摘录关键分支：

```text
    fn try_allocate_in(
        capacity: usize,
        init: AllocInit,
        alloc: A,
        elem_layout: Layout,
    ) -> Result<Self, TryReserveError> {
        // We avoid `unwrap_or_else` here because it bloats the amount of
        // LLVM IR generated.
        let layout = match layout_array(capacity, elem_layout) {
            Ok(layout) => layout,
            Err(_) => return Err(CapacityOverflow.into()),
        };

        // Don't allocate here because `Drop` will not deallocate when `capacity` is 0.
        if layout.size() == 0 {
            return Ok(Self::new_in(alloc, elem_layout.alignment()));
        }

        let result = match init {
            AllocInit::Uninitialized => alloc.allocate(layout),
            #[cfg(not(no_global_oom_handling))]
            AllocInit::Zeroed => alloc.allocate_zeroed(layout),
        };
        let ptr = match result {
            Ok(ptr) => ptr,
            Err(_) => return Err(AllocError { layout, non_exhaustive: () }.into()),
        };
        …
    }
```

布局计算先验证容量能否表示。零容量和零大小元素都能走不分配的分支；否则按初始化要求选择普通分配或清零分配。`with_capacity` 不承诺空余部分含有初始化的值。

布局计算中，`repeat_packed` 按照元素布局计算数组布局并捕获不能表示的大小。源码把这个错误映射到 `CapacityOverflow`，区别于布局有效但分配器不能满足请求时的 `AllocError`：

```text
const fn layout_array(cap: usize, elem_layout: Layout) -> Result<Layout, TryReserveError> {
    // This is only used with `elem_layout`s which are those of real rust types,
    // which lets us use the much-simpler `repeat_packed`.
    debug_assert!(elem_layout.size() == elem_layout.pad_to_align().size());

    elem_layout.repeat_packed(cap).map_err(const |_| CapacityOverflow.into())
}
```

非空占位值还有一个用途：让空的 `Vec` 也能维持“指针字段非空”的内部不变量，用于某些布局优化。注意此处的“非空”不等同于“有可访问的内存”。

`RawVecInner<A>` 保存未指定元素类型的 `NonNull<u8>`。外层的 `PhantomData<T>` 把元素类型纳入型变等类型属性，但不会在运行时增加一份 `T`。

历史版本用 `Unique<T>` 等包装器来同时表达指针与拥有关系；不同标准容器现在不保证使用相同包装器。真正决定元素析构和缓冲区释放的是类型的代码与不变量，不能仅靠字段名判断。

例如，零容量和零大小元素都会避免分配，但返回的容量不同：

| 创建方式 | 长度 | 容量 |
| --- | --- | --- |
| `Vec::<u32>::new()` | 0 | 0，不预分配。 |
| `Vec::<u32>::with_capacity(n)` | 0 | 至少为 `n`；预留空间没有初始化元素。 |
| `Vec::<()>::new()` | 0 | `usize::MAX`；零大小类型不为元素分配字节。 |
