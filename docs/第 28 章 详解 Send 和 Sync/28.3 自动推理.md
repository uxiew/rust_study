# 28.3 自动推理

Send 和 Sync 就是一种常见的标记 traits（Marker Trait）。
它们并没有任何方法或关联类型，仅仅标记了该类型可以被安全地在多个线程之间共享（Sync）或传递（Send）。
使用这些标记 traits，编译器可以在编译时对类型进行检查，确保它们可以安全地在多个线程中使用。

例如，`std::marker` 收录了一批用于说明类型属性的 trait。类型是否实现某个标记，可以用来约束泛型参数，而不需要调用该 trait 的方法。

那么为什么要定义这样一组特殊的 trait，还叫做 marker trait ？这些 trait 有什么特别之处？

我们称这些 trait 为“标记”，就是为了区分接口的实现和**向编译器提供有关类型属性的信息**，这两者都是在 Rust 中通过 trait 完成的。
然而，它们并没有什么特别之处。与所有其他 trait 一样，这些都是正常的 trait 。这只是我们人类的语义上的名称。

> 摘自：[What is a marker trait in Rust?](https://stackoverflow.com/questions/76445707/what-is-a-marker-trait-in-rust)


标准库中有几个常见的标记 trait。如果类型 `T` 实现：

- `Copy`：赋值或传参时可以隐式复制值，而不是移动所有权。
- `Send`：值可以跨线程边界发送。
- `Sync`：共享引用可以跨线程发送，即 `&T: Send`。
- `Sized`：大小在编译时已知。它由编译器实现，不能手写。
- `Unpin`：即使处在 `Pin` 的包装中，类型也不依赖固定的地址。

上面的 `Send`、`Sync` 和 `Unpin` 都是 auto trait；`std::panic` 中还有 `UnwindSafe` 和 `RefUnwindSafe`。下面是 `Send` 的标准库声明：

```text
pub unsafe auto trait Send {}
```

这种特殊语法曾称为 OIBIT，现在称为自动 trait。当没有适用的显式实现时，编译器会按成员推导：一个需要自动实现某 trait 的结构体，它的所有成员也必须满足相应的要求。

## 28.3.1 auto trait

::: tip 新版变化
Rust 1.100 稳定版可以使用标准库提供的 auto trait。自定义 `auto trait` 仍需 Nightly 的 [`auto_traits`](https://doc.rust-lang.org/unstable-book/language-features/auto-traits.html)，显式写负向实现还需 [`negative_impls`](https://doc.rust-lang.org/unstable-book/language-features/negative-impls.html)。稳定版若需让包装类型保持线程亲和性，可加入 `PhantomData<Rc<()>>`，无需实际分配一个 `Rc`。
:::

```rust:{channel:"nightly",edition:"2024"}
#![feature(auto_traits, negative_impls)]

auto trait Shareable {}
struct Local;
impl !Shareable for Local {}

struct Envelope(Local);

fn check<T: Shareable>() {}

fn main() {
    check::<i32>();
    // check::<Envelope>(); // E0277：成员 Local 没有实现 Shareable
}
```

在示例中，`i32` 没有负向实现，编译器自动为它实现了 `Shareable`。`Local` 则通过 `impl !Shareable` 选择退出。由于 `Envelope` 持有 `Local`，它也不会自动实现这个 trait；若取消注释，编译器会拒绝调用 `check::<Envelope>()`。

## 28.3.2 从成员推导 Send 和 Sync

例如，概念上可以用以下标准库实现摘录解释指针和引用的行为。这是摘录，不是用户代码中可重复实现的接口：

```text
impl<T: ?Sized> !Send for *const T {}
impl<T: ?Sized> !Send for *mut T {}
unsafe impl<T: ?Sized + Sync> Send for &T {}
```

另外，`&mut T: Send` 要求 `T: Send`。拥有共享引用的两个线程可能同时读同一个值，所以共享引用需要 `T: Sync`；可变引用是独占借用，移动它则需要内部值能够跨线程访问。

```rust
struct Message {
    text: String,
}

fn require_send_sync<T: Send + Sync>() {}

fn main() {
    require_send_sync::<Message>();
}
```

大多数自定义类型不需要手写 `Send` 或 `Sync`。包含 `Rc<T>` 或裸指针的类型，默认不会得到相应的自动实现；例如，在 FFI 封装中，编译器并不知道裸指针指向的资源是否绑定于创建它的线程，或资源能否在另一个线程析构。

当类型确实满足安全契约但编译器无法推知时，库的作者可以写正向实现。例如，下面这段是实现的写法，而不是可以套用到所有裸指针包装上的安全承诺：

```text
unsafe impl Send for Wrapper {}
impl !Sync for Wrapper {} // 负向实现需 Nightly 的 negative_impls
```

`unsafe` 用在正向实现上，意味着实现者要论证跨线程移动不会破坏安全性；错误的承诺可能使下游的安全代码产生未定义行为。负向实现没有这种承诺，因此不能写 `unsafe impl !Sync`。

例如，下面的包装只把裸指针当作可比较的标记，不解引用，也没有负责释放指针目标的析构逻辑。对这个受限的类型，手写 `Send` 是成立的：

```rust
use std::{ptr, thread};

struct Bar {
    ptr: *const (),
}

// SAFETY: 此类型只检查指针是不是空值，不会解引用或释放目标。
unsafe impl Send for Bar {}

fn main() {
    let value = Bar { ptr: ptr::null() };
    assert!(thread::spawn(move || is_null(value)).join().unwrap());
}

fn is_null(value: Bar) -> bool {
    value.ptr.is_null()
}
```

如果以后加上了访问目标的操作，或者改成在线程中释放目标，就必须重新检查这个承诺。另外，并非所有标记 trait 都能由开发者手动实现：试图为自己的类型实现 `Sized` 会得到 [E0322](https://doc.rust-lang.org/stable/error_codes/E0322.html)。
