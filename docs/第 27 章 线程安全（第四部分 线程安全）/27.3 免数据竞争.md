# 27.3 免数据竞争

Rust 的多线程 API 表面简单，却能在跨越线程边界时做不少检查。正可谓：

> 胸有激雷而面如平湖者，可拜上将军也！

我们做几个实验，看看多个线程试图读写同一个变量时会发生什么。

## 27.3.1 闭包怎样获得数据

我们创建一个子线程，让它试着修改外部的局部变量：

```rust,compile_fail,no_run
use std::thread;

fn main() {
    let mut health = 12;
    thread::spawn(|| health *= 2);
}
```

预期报错 **E0373**：`spawn` 要求闭包满足 `'static`，因为线程可能活得比调用者更久；这里闭包捕获了对局部变量的短期可变借用。

| 捕获方式 | 线程拿到什么 |
| --- | --- |
| 借用局部变量再用 `spawn` | 局部引用可能失效，编译器拒绝 |
| 用 `move` 捕获 `Copy` 值（如整数） | 值的副本，不会改变原变量 |
| 用 `move` 捕获非 `Copy` 值（如 `Vec`） | 值的所有权，调用者不能再使用原变量 |

给闭包加上 `move`，原先的错误就消失了。执行时，子线程中的值加倍，主线程中的值却没有变化。因为整数是 `Copy`，闭包拿到的是一份副本：

```rust
use std::thread;

fn main() {
    let health = 12;
    let doubled = thread::spawn(move || {
        let mut health = health;
        health *= 2;
        health
    }).join().unwrap();
    assert_eq!((health, doubled), (12, 24));
}
```

如果使用的不是 `Copy` 类型，又会怎样呢？先在闭包中借用局部 `Vec`：

```rust,compile_fail,no_run
use std::thread;

fn main() {
    let mut values = Vec::new();
    thread::spawn(|| values.push(1));
}
```

预期报错 **E0373**：和借用 `health` 一样，闭包借用的局部变量可能比线程先销毁。加上 `move` 后，再从原线程读取它，会遇到另一个错误：

```rust,compile_fail,no_run
use std::thread;

fn main() {
    let mut values = vec![1];
    thread::spawn(move || values.push(2)).join().unwrap();
    println!("{values:?}");
}
```

预期报错 **E0382**：`values` 已移入闭包，`join` 不会把所有权还给调用者。

## 27.3.2 借用局部数据的作用域线程

::: tip 新版变化
从 Rust 1.63 起，稳定版的 `thread::scope` 可以借用外部的局部变量。作用域返回前会等待所有未手动 `join` 的作用域线程，因此下面不需要 `move`，也不需要 `Arc`。
:::

```rust
use std::thread;

fn main() {
    let mut health = 12;
    thread::scope(|scope| {
        scope.spawn(|| health *= 2);
    });
    assert_eq!(health, 24);
}
```

## 27.3.3 数据竞争与同步

**数据竞争**指不同线程以无法保证先后顺序的方式访问同一内存位置，其中至少一个是写入，且并非所有访问都是原子的。它需要下列条件同时成立：

- 数据共享：多个线程访问同一份数据。
- 数据修改：至少有一个线程写入。
- 没有适当的同步：冲突访问之间没有建立先后关系，并且至少有一个是非原子访问。

要避免数据竞争，可以打破其中任一个条件。比如 Actor 模型用消息传递替代对可变数据的直接共享；函数式风格常用不可变的数据减小共享写入的范围。当确实要共享可变状态时，可以使用锁或合适的原子操作。

还可以回顾第二部分的规则：共享引用允许多个读者；可变借用只能独占。像 `Mutex` 的共享引用则不直接暴露内部的可变引用，必须先拿到独占守卫。所有权和同步 API 相配合，才使这种共享在安全 Rust 中成立。

C/C++ 同样可以正确地实现并发，但程序员必须确保每次共享访问都使用了正确的同步方式。安全 Rust 把这部分职责放进类型与库的契约中，调用者不必逐一审查每个调用点。契约的前提仍是：底层 `unsafe` 实现正确。数据竞争的保证不覆盖死锁或结果依赖调度的逻辑错误，后面会看到这些例子。
