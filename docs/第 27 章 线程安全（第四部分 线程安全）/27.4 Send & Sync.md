# 27.4 Send & Sync

下面来简单讲解一下 Rust 是如何实现免疫数据竞争的。Rust 线程安全背后的功臣是两个特殊的 trait。

* `std::marker::Sync`

如果类型 T 实现了 Sync 类型，那说明在不同的线程中使用`&T`访问同一个变量是安全的。

* `std::marker::Send`

如果类型 T 实现了 Send 类型，那说明这个类型的变量在不同的线程中传递所有权是安全的。


Rust 把类型根据 Sync 和 Send 做了分类。这样做起什么作用呢？当然是用在“泛型约束”中。并发 API 按需要求其中的类型满足 `Send` 或 `Sync`。这样一来，“孙猴子就永远也逃不出如来佛的手掌心”了。

[`std::thread::spawn`](https://doc.rust-lang.org/std/thread/fn.spawn.html) 的签名如下（只展示接口）：

```text
pub fn spawn<F, T>(f: F) -> JoinHandle<T>
where
    F: FnOnce() -> T + Send + 'static,
    T: Send + 'static,
```

`F: Send` 是因为闭包要被送入子线程；`T: Send` 是因为子线程的返回值可能通过 `join` 送回调用者。`'static` 不意味着值必须活到进程退出，而是其中不能含有短期借用。

`spawn` 没有直接要求 `Sync`。但闭包捕获 `&T` 时，需要把这份共享引用送到子线程，这时 `T: Sync` 就派上用场了。

因此，闭包即使采用 `move` 捕获，也并不一定能跨线程。例如捕获 `Rc<T>` 时，其他克隆可能仍在原线程，引用计数不是原子操作。这个错误通常在把闭包交给 `spawn` 时就会被发现。

全局变量则是另一条可能绕过“捕获”的路径：线程可以不捕获任何数据，仍访问全局变量。因此共享的 `static` 也受类型约束，见第 29.8 节。只要底层的 `unsafe` 实现遵守安全契约，安全代码不会产生数据竞争；但这不保证没有死锁。
