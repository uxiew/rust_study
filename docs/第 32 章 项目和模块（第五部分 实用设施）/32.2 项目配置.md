# 32.2 项目配置

在 `Cargo.toml` 中，我们可以指定一个包的信息与依赖。`[package]` 的 `edition` 指定包的源代码使用哪一版 Rust 语言规则；依赖可以使用不同的 Edition。这些依赖既可以是来自官方的 crates.io，也可以是某个 git 仓库地址，还可以是本地文件路径。示例如下：

```toml
[package]
name = "hello"
version = "0.1.0"
edition = "2024"

[dependencies]
serde = "1"
regex = { version = "1", features = ["unicode"] }
rand = { git = "https://github.com/rust-random/rand" }
my_local = { path = "../my_local", version = "0.1.0" }

[target.i686-unknown-linux-gnu.dependencies]
openssl = "0.10"

[build-dependencies]
cc = "1"

[dev-dependencies]
tempfile = "3"
env_logger = "0.11"

[dependencies.nom]
version = "8"
default-features = false
features = ["alloc"]
```

下面是几类依赖的用途：

| 表 | 用途 | 添加方式示例 |
| --- | --- | --- |
| `[dependencies]` | 普通的库和二进制目标 | `cargo add serde` |
| `[dev-dependencies]` | 测试、示例和基准测试；普通构建不启用 | `cargo add --dev tempfile` |
| `[build-dependencies]` | 构建脚本 `build.rs` | `cargo add --build cc` |

用 `cargo remove` 可以从 `Cargo.toml` 移除依赖。`[target.i686-unknown-linux-gnu.dependencies]` 中的依赖则只用于对应的编译目标。

`[dependencies.nom]` 展开了单个依赖项的配置，与把这些字段写成一行等价：

- `version = "8"` 允许选择满足要求的 8.x 版本，不是精确锁定；Git 或本地依赖也可以附带版本约束。
- `default-features = false` 不主动启用默认特性；`features = ["alloc"]` 启用 `nom` 的 `alloc` 特性。特性不是任意开关，名称和用途由依赖包定义。同一解析范围内其他依赖也可能为该包启用更多特性。

更多内容见[依赖配置](https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html)和[依赖特性](https://doc.rust-lang.org/cargo/reference/features.html#dependency-features)。

## crate 版本号

Rust 里面的 crate 都是自带版本号的。版本号采用的是[语义版本的思想](http://semver.org/)。基本意思如下：

- `1.0.0` 以前的版本是不稳定版本，如果出现了不兼容的改动，升级次版本号，比如从 `0.2.15` 升级到 `0.3.0`；

- 在 `1.0.0` 版本之后，如果出现了不兼容的改动，需要升级主版本号，比如从 `1.2.3` 升级到 `2.0.0`；

- 在 `1.0.0` 版本之后，如果是兼容性的增加 API，虽然不会导致下游用户编译失败，但是增加公开的 API 情况，应该升级次版本号。

下面详细讲一下在`[dependencies]`里面的几种依赖项的格式：

（1）来自 crates.io 的依赖

绝大部分优质开源库，作者都会发布到官方仓库中，所以我们大部分的依赖都是来自于这个地方。在 crates.io 中，每个库都有一个独一无二的名字，我们要依赖某个库的时候，只需指定它的名字及版本号即可；

```toml
[dependencies]
lazy_static = "1.0"
```

指定版本号的时候，可以使用模糊匹配的方式。

- `^`符号，如`^1.2.3`代表`1.2.3<=version<2.0.0`；

- `~`符号，如`~1.2.3`代表`1.2.3<=version<1.3.0`；

- `*`符号，如`1.*`代表`1.0.0<=version<2.0.0`；

- 比较符号，比如`>=1.2.3`、`>1.2.3`、`<2.0.0`、`=1.2.3`含义基本上一目了然，还可以把多个限制条件合起来用逗号分开，比如`version = ">1.2, <1.9"`。

直接写一个数字的话，等同于`^`符号的意思。所以`lazy_static="1.0"`等同于`lazy_static="^1.0"`，含义是`1.0.0<=version<2.0.0`。Cargo 会结合锁文件、其他依赖约束和解析器配置选择版本；没有锁定结果且其他条件允许时，通常优先选择较新的兼容版本。

（2）来自 git 仓库的依赖

只写 `git = "…"` 就会跟随仓库的默认分支。也可以用 `branch` 指定分支，例如：

```toml
rand = { git = "https://github.com/rust-random/rand", branch = "master" }
```

或者用 `rev` 指定某次提交：

```toml
rand = { git = "https://github.com/rust-random/rand", rev = "98473ee6f9b44eb85154b59b67adade7f2a9b8a1" }
```

还可以指定对应的 tag 名字：

```toml
rand = { git = "https://github.com/rust-random/rand", tag = "0.9.2" }
```

（3）来自本地文件路径的依赖

指定本地文件路径，既可以用绝对路径，也可以用相对路径。相对路径从写下这个依赖的 `Cargo.toml` 所在目录算起：

```toml
[dependencies]
my_local = { path = "../my_local" }
```

第一次构建项目时，Cargo 会根据 `Cargo.toml` 中的约束解析依赖并写入 `Cargo.lock`。锁文件记录具体版本和来源；下次构建优先复用这些结果。如果清单变了，Cargo 会重新解析需要调整的部分。`cargo build --locked` 要求不改动锁文件。

通常把 `Cargo.lock` 纳入版本管理，可以让本仓库的开发和 CI 使用一致的依赖版本；即使是库项目，提交这一文件也不会锁定下游用户的依赖，下游项目有自己的锁文件。锁定依赖版本不等于保证不同机器编译出来的产物逐字节相同。

Rust 2015 中，通常还要在源码中用 `extern crate hello;` 声明外部 crate，也可以用 `extern crate hello as hi;` 起别名。从 Rust 2018 起，Cargo 传给编译器的依赖通常可直接用 `hello::…` 引用，想换名字可以用 `use hello as hi;`，或在清单中为依赖配置别名。

## Profiles 配置文件

Cargo 有两个主要的配置文件：在运行 `cargo build` 命令时使用的 dev 配置文件，在运行 `cargo build --release` 时使用的 release 配置文件。它们都有各自的默认值。所以在运行构建时，我们会看到如下输出：

```text
$ cargo build
    Finished dev [unoptimized + debuginfo] target(s) in 0.00s
$ cargo build --release
    Finished release [optimized] target(s) in 0.00s
```

我们可以通过在项目 `Cargo.toml` 文件中设置 `[profile.*]` 配置，来自定义构建配置：

```toml
[profile.dev]
opt-level = 0

[profile.release]
opt-level = 3
```

`opt-level` 设置控制对你代码的优化数量，可用 `0` 到 `3`，也可用侧重体积的 `"s"` 和 `"z"`。dev 默认 `0`，减少优化以加快迭代；release 默认 `3`，侧重运行性能。

更多信息查看 [Cargo-Profiles](https://doc.rust-lang.org/cargo/reference/profiles.html)

## 32.2.1 cargo 配置文件

cargo 也支持配置文件。配置文件可以定制 cargo 的许多行为，就像我们给 git 设置配置文件一样。
类似的，cargo 的配置文件可以存在多份，它们之间有优先级关系。你可以为某个文件夹单独提供一份配置文件， 例如在当前文件夹下的 `.cargo/config.toml` 文件，也可以提供一个全局的默认配置，为 `$HOME/.cargo/config.toml` 文件或者不带 `.toml`扩展名的文件。
Cargo 对 `.toml` 扩展名的支持是在 1.39 版本中添加的，已经是首选形式了。如果这两种形式的配置文件都存在，Cargo 优先使用不带扩展名的文件，所以推荐新建 `config.toml`，不要同时保留两份。

下面是一份配置示例：

```toml
[build]
jobs = 1                      # 并行构建任务数
rustflags = ["-C", "debuginfo=1"] # 额外的 rustc 参数

[term]
verbose = false           # 是否打印详细信息
color = "auto"            # 控制彩色显示

[alias]                   # 设置命令别名
rr = "run --release"
```

更详细的信息请参考[官方文档：cargo-Configuration](https://doc.rust-lang.org/cargo/reference/config.html#configuration)。

## 32.2.2 workspace

cargo 的 workspace 概念，是为了解决多 crate 的互相协调问题而存在的。假设现在我们有一个比较大的项目。
我们把它拆分成了多个 crate 来组织，就会面临一个问题：不同的 crate 会有各自不同的`Cargo.toml`，编译的时候它们会各自产生不同的`Cargo.lock`文件，我们无法保证所有的 crate 对同样的依赖项使用的是同样的版本号。

为了让不同的 crate 之间能共享一些信息，cargo 提供了一个 workspace 的概念。一个 workspace 可以包含多个项目，这里我们只展示一种常见的用法：包含二进制文件（project1）和一个库（lib1）的工作空间。这里让提供主要功能的二进制包依赖这个库。

所有成员共享一个 `Cargo.lock` 和默认的输出目录 `target/`。它们统一解析依赖，但不兼容的版本要求仍可能给同一个外部库选出多个版本。

workspace 同样是用 `Cargo.toml` 来管理的。我们可以把所有的项目都放到一个文件夹下面。在这个文件夹下写一个`Cargo.toml`来管理这里的所有项目。
`Cargo.toml` 文件中要写一个 `[workspace]` 的配置，比如：

```toml
[workspace]

members = ["project1", "lib1"]
resolver = "3"
```

这里的根清单没有 `[package]`，不能从包的 Edition 推断解析器；`resolver = "3"` 显式选用了 Edition 2024 对应的解析规则。

构建后，整个文件夹的目录结构如下：

```text
├── Cargo.lock
├── Cargo.toml
├── project1
│   ├── Cargo.toml
│   └── src
│       └── main.rs
├── lib1
│   ├── Cargo.toml
│   └── src
│       └── lib.rs
└── target
```

project1 中需要引入 lib1 的话，就需要设置 `project1/Cargo.toml`：

```toml
[dependencies]
lib1 = { path = "../lib1" }
```

我们可以在 workspace 的根目录执行 `cargo build` 等命令，我们还可以指定运行哪个 二进制项目，例如运行 project1 项目：

```bash
cargo run -p project1
```

如果几位成员希望共用一套依赖声明，可在根清单用 `[workspace.dependencies]` 定义，再在成员中写 `regex = { workspace = true }` 继承。

## 32.2.3 build.rs

cargo 工具还允许用户在正式编译开始前执行一些自定义的逻辑。
方法是在根目录下创建`build.rs`文件，自定义逻辑就写在`build.rs`文件里面。
在执行`cargo build`的时候，cargo 会先把这个`build.rs`编译成一个可执行程序，然后运行这个程序，做完后再开始编译真正的 crate。

`build.rs`一般用于下面这些情况：

- 提前调用外部编译工具，比如调用`gcc`编译一个 C 库；
- 在操作系统中查找 C 库的位置；
- 根据某些配置，自动生成源码；
- 执行某些平台相关的配置。

`build.rs`里面甚至可以再依赖其他的库。只列在 `[dependencies]` 或 `[dev-dependencies]` 中的依赖对 `build.rs` 不可见。
我们需要在 `build-dependencies` 中指定需要的依赖，可以通过 `cargo add --build cc` 添加构建依赖：

```toml
[build-dependencies]
cc = "1"
```

`build.rs`里面如果需要读取当前 crate 的一些信息，可以通过环境变量来操作。
cargo 在执行这个程序之前就预先设置好了一些环境变量，比较常用的有下面几种。

- `CARGO_MANIFEST_DIR`

当前包的 `Cargo.toml` 所在目录。

- `CARGO_PKG_NAME`

当前包的名字。

- `OUT_DIR`

`build.rs` 的输出路径。如果要在 `build.rs` 中生成代码，那么生成的代码就要存在这个文件夹下。

- `HOST`

运行构建脚本的平台。`TARGET` 是要构建的目标平台，交叉编译时可能与 `HOST` 不同。

- `OPT_LEVEL`

优化级别。

更多的[环境变量](https://doc.rust-lang.org/cargo/reference/environment-variables.html)请参考 cargo 的标准文档。

下面还是用一个完整的示例演示一下 `build.rs` 功能如何使用。

### 构建时注入环境变量

假设要在程序里显示当前 Git 标签、提交和构建日期。先在有提交的项目仓库里创建标签：

```bash
git tag -a v0.1.2 -m 'new version'
```

在 `src/main.rs` 中用 `option_env!` 在编译时读取这些信息。没获得 Git 信息时仍然能构建：

```rust
fn main() {
    println!("Hello, world!");
    println!("version: {}", option_env!("GIT_VERSION").unwrap_or("unknown"));
    println!("commit: {}", option_env!("GIT_COMMIT").unwrap_or("unknown"));
    println!("date: {}", option_env!("BUILD_DATE").unwrap_or("unknown"));
}
```

运行 `cargo add --build chrono@0.4`，将日期格式化的依赖加入 `Cargo.toml`：

```toml
[build-dependencies]
chrono = "0.4"
```

然后编写 `build.rs`（需要上面的 `chrono` 构建依赖）：

```rust,ignore,no_run
use chrono::Utc;
use std::process::Command;

fn git_value(args: &[&str]) -> Option<String> {
    let output = Command::new("git").args(args).output().ok()?;
    if !output.status.success() {
        return None;
    }
    let text = String::from_utf8(output.stdout).ok()?;
    Some(text.trim().to_owned())
}

fn main() {
    if let Some(tag) = git_value(&["describe", "--tags", "--abbrev=0"]) {
        println!("cargo::rustc-env=GIT_VERSION={tag}");
    }
    if let Some(commit) = git_value(&["rev-parse", "HEAD"]) {
        println!("cargo::rustc-env=GIT_COMMIT={commit}");
    }
    println!("cargo::rustc-env=BUILD_DATE={}", Utc::now().to_rfc3339());
}
```

当 Cargo 运行 `build.rs` 时，会捕捉以 `cargo::rustc-env=` 开头的指令，并在随后编译程序时定义相应的变量。`cargo::` 双冒号语法需要 Cargo 1.77 或更新版本。它不同于在运行时调用 `std::env::var`：构建脚本写入的值已编进可执行文件。

执行 `cargo run` 后，输出类似：

```text
Hello, world!
version: v0.1.2
commit: f6b7fc65ef00e3b2d27886ab9ecf243b4ef6549b
date: 2023-10-17T14:38:43.833297+00:00
```

这里演示的是构建时注入，不是 Git 状态跟踪。仅创建标签或提交，并不保证 Cargo 重跑脚本；要手动刷新可先执行 `cargo clean`。生产项目可按需用 [`cargo::rerun-if-changed`](https://doc.rust-lang.org/cargo/reference/build-scripts.html#rerun-if-changed) 跟踪输入；如需可复现构建，不应直接嵌入每次构建的当前时间。

### 构建时生成 rs 文件

如果希望编译时获得一个 Rust 常量，也可以让构建脚本生成源码。下面是另一个独立的项目：

```bash
cargo new --bin with_commit_hash
```

假设生成的常量如下：

```rust
pub const CURRENT_COMMIT_ID: &str = "123456789ABCDEF";
```

查找当前 Git 提交可以使用 `git rev-parse HEAD`。在新项目根目录下创建 `build.rs`：

```rust,no_run
use std::{env, fs, io, path::PathBuf, process::Command};

fn main() -> io::Result<()> {
    let out_dir = PathBuf::from(env::var_os("OUT_DIR").expect("需要由 Cargo 运行"));
    let commit = Command::new("git")
        .args(["rev-parse", "HEAD"])
        .output()
        .ok()
        .filter(|output| output.status.success())
        .and_then(|output| String::from_utf8(output.stdout).ok());
    let commit = commit.as_deref().map(str::trim).unwrap_or("unknown");
    let source = format!("pub const CURRENT_COMMIT_ID: &str = {commit:?};\n");
    fs::write(out_dir.join("commit_id.rs"), source)
}
```

用 `Command` 调用外部程序后，先检查退出状态，再读取标准输出并去掉换行；拿不到提交就生成 `unknown`。输出文件写在 Cargo 提供的 `OUT_DIR` 内，不修改 `src/`。格式化时用 `{commit:?}` 生成带引号的字符串字面量。

生成源码后，`src/main.rs` 用 `include!` 将其包含进来。这段代码需要由 Cargo 构建，并依赖上面生成的文件：

```rust,ignore,no_run
include!(concat!(env!("OUT_DIR"), "/commit_id.rs"));

fn main() {
    println!("Current commit id is: {}", CURRENT_COMMIT_ID);
}
```

`concat!` 将输出目录和文件名组合成路径；`include!` 在编译阶段把文件解析到当前位置，所以 `main` 可以像访问本文件中的常量一样访问它。可以在有提交与无提交的项目里分别运行 `cargo run` 对照结果。与前面的例子一样，Git 提交变化不会自动保证构建脚本重跑。
