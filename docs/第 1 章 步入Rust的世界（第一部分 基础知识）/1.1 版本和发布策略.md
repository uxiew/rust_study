# 1.1 版本和发布策略

Rust 编程语言是开源的，编译器的源码位于 rust-lang/rust，语言设计和相关讨论位于 RFC 项目中。对于想深入研究这门语言的读者来说，这是一个非常好的消息，大家可以通过研读开放的源代码和技术文档了解到很多书本上没有讲解过的知识。任何一个开发者都可以直接给这个项目提 bug，或者直接贡献代码。Rust 项目是完全由开源社区管理和驱动的，社区的氛围非常友好。

Rust 编译器的版本号采用了“语义化版本号”（Semantic Versioning）规划。在这个规则之下，版本格式为：`主版本号.次版本号.修订号`。

版本号递增规则如下。

- 主版本号：当你做了不兼容的 API 修改
- 次版本号：当你做了向下兼容的功能性新增
- 修订号：当你做了向下兼容的问题修正

Rust 的第一个正式版本号是 1.0，是 2015 年 5 月发布的。从那以后，只要版本没有出现大规模的不兼容的升级，大版本号就一直维持在“1”，而次版本号会逐步升级。Rust 一般以 6 个星期更新一个正式版本的速度进行迭代。

## 工具链渠道

Rust 要同时兼顾快速迭代和稳定性，因此提供三个发布渠道，读者可以按自己的需要和能承受的风险选择。

日常学习和生产项目用 Stable。只有明确要求不稳定特性的例子才需要 Nightly；使用语言特性时，还要在 crate 根文件开启对应的 `#![feature(...)]`。

| 渠道 | 用途 |
| --- | --- |
| Stable | 正式发行；约六周一个新版本 |
| Beta | 试用下一版 Stable，提前发现回归 |
| Nightly | 试用最新编译器和实验特性；不保证功能稳定 |

下面是发行分支的简图。未稳定的 feature gate 不会因发行分支晋升就自动在 Stable 开放。

## 工具链版本与 Edition

上图画的是工具链的发行流程，不等同于单项功能的设计流程。重大设计通常先写成 [RFC（Request for Comments）](https://rust-lang.github.io/rfcs/)，说明目标、设计方案、缺点和备选方案，由社区讨论并由负责的团队审议。接受 RFC 并不意味着功能已经稳定：实现可以先用 feature gate 在 Nightly 上试用，再根据反馈修改、撤销或决定稳定。学习 Rust 时也可以读 RFC 的讨论，了解设计是如何推导出来的，而不只是记结论。

2017 年提出的 [epoch 方案](https://rust-lang.github.io/rfcs/2052-epochs.html)，也就是后来的 Edition，试图解决另一类问题：如果要引入一个关键字，旧项目很可能已经用它命名了变量；如果始终不能改变这条规则，新语言功能就会受到限制。Edition 让旧 crate 保留原先的解释，新 crate 可以选择新规则，不需要一次迁移所有依赖。

::: tip 新版变化
本站示例使用 Rust **1.100.0 Stable** 和 **Edition 2024**。前者是编译器版本；后者是 crate 选择的语言规则，写在 `Cargo.toml` 的 `edition` 字段中。同一个编译器可构建不同 Edition 的 crate，它们也能在依赖图中共存。
:::

例如，`gen` 在 Edition 2024 中是保留关键字；旧 Edition 的同名标识符可迁移为 `r#gen`。保留关键字并不表示 `gen` 块已经稳定。

新项目用 `cargo new hello --edition 2024`。迁移旧项目时，先在原 Edition 下执行 `cargo fix --edition`，再将 `Cargo.toml` 改为 `edition = "2024"` 并运行测试。详见 [Edition Guide](https://doc.rust-lang.org/edition-guide/editions/creating-a-new-project.html) 和 [版本发布流程](https://doc.rust-lang.org/book/appendix-07-nightly-rust.html)。

日常查阅类型和方法时，可直接打开 [Rust 标准库文档](https://doc.rust-lang.org/std/)；需要和本站基线对照时，使用 [1.100.0 的标准库文档](https://doc.rust-lang.org/1.100.0/std/)。

## 为什么分开管理工具链和 Edition

原书写于第一个新 Edition 发布之前。它用“旧项目已经使用某个名字，新版本想把它变成关键字”解释兼容性的两难。现在回看，重要的不是要求所有项目同时改名，而是给改动一个边界：编译器仍理解旧语言规则，迁移工具提示可改的地方，项目自行决定何时采用新规则。比如维护一个较老的库时，可以先升级工具链、维持原 Edition 并运行测试；等迁移工作完成后再切换 Edition。发布到 crates.io 的库也不要求使用者和它采用相同 Edition。

同样，选择 Nightly 不会自动开启每个实验功能，改用新 Edition 也不意味着可以使用所有 Nightly 特性。遇到不能编译的示例时，可以先用 `rustc --version` 检查实际工具链，再看包的 `Cargo.toml`，最后核对该功能的稳定版本或特性门槛。这样可以区分“工具链太旧”“Edition 不匹配”和“功能仍是实验性的”，而不是盲目改编译选项。
