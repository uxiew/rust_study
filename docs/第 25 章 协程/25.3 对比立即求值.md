# 25.3 对比立即求值

从代码组织上看，迭代器模式已经多了一层抽象。刚开始学习时，更自然的写法可能是用一个循环把数据全部算出来，再交给后续代码处理。

如果要收集整个 Fibonacci 序列，也可以直接循环，把每一项存入 `Vec`。这里会先生成全部能用 `u64` 表示的项，再读取前六项。

```rust
fn collect_fibonacci() -> Vec<u64> {
    let mut values = vec![1, 1];
    let (mut current, mut next) = (1_u64, 1_u64);
    while let Some(sum) = current.checked_add(next) {
        values.push(sum);
        (current, next) = (next, sum);
    }
    values
}

fn main() {
    let values = collect_fibonacci();
    assert_eq!(&values[..6], &[1, 1, 2, 3, 5, 8]);
}
```

此时，读取 `values` 的过程仍可以使用迭代器，但 Fibonacci 数列已经全部生成。这和前两节一边计算、一边消费的写法不同。

| 写法 | 只需要前六项 | 需要重复读取整个序列 |
| --- | --- | --- |
| 迭代器 + `take(6)` | 只求前六项，不必分配完整容器 | 可重建迭代器，或第一次就收集结果 |
| 先收集到 `Vec` | 仍会算出并保存剩余项 | 可以重复借用并按下标访问 |

立即求值的代价是先算完并保存所有数据。如果使用者只需要使用这个序列的前 10 个数据呢？如果是方案二迭代器的那种写法，使用者可以选择遍历 10 个元素后就提前 `break`；后面的数据既不需要生产，也不需要消费，还节省了一个临时的占用很大内存空间的容器，这就是“惰性求值”的好处。手写迭代器虽然能按需计算，却需要人工推理：哪些数据是需要存储在迭代器成员中的，哪些是不需要的，进入 `next` 方法时如何读取上一次的状态，退出 `next` 方法时如何保存这一次的状态等。这些都是“心智负担”。业务逻辑越复杂，这个负担越严重。
