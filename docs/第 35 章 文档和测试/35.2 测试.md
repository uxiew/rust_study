# 35.2 测试

先按要验证的对象选择测试：

| 类型 | 常放在哪里 | 验证什么 |
| --- | --- | --- |
| 单元测试 | `src/` 的 `#[cfg(test)] mod tests` | 单个函数或模块，可测试父模块的私有项 |
| 集成测试 | `tests/` 下的独立目标 | 从包外部的视角验证库的公开接口或可执行文件 |
| 文档测试 | 库的 Rust 文档代码块 | 文档中的使用示例是否与代码一致 |
| 基准测试 | `benches/` | 执行耗时等性能指标 |

## 单元测试

`cargo new --lib gcd` 会生成带单元测试的库模板。单元测试可以跟业务代码放在同一文件里：改一个函数时，相关测试就在附近；因为测试模块是子模块，还可以访问父模块定义的私有函数。

先新建项目：

```bash
cargo new --lib gcd
cd gcd
```

把下面的辗转相除法示例保存为 `src/lib.rs`，再运行 `cargo test`：

```rust
pub fn gcd(mut a: u64, mut b: u64) -> u64 {
    while b != 0 {
        (a, b) = (b, a % b);
    }
    a
}

#[cfg(test)]
mod tests {
    use super::gcd;

    #[test]
    fn common_divisor() {
        assert_eq!(gcd(54, 24), 6);
    }

    #[test]
    fn with_zero() {
        assert_eq!(gcd(10, 0), 10, "gcd(a, 0) 应返回 a");
    }
}
```

`#[cfg(test)]` 让模块只在构建该目标的测试版本时编译；`#[test]` 标记要运行的函数。测试是子模块，所以用 `use super::gcd` 把父模块中的名字引入作用域。`assert_eq!` 的最后一个参数可提供断言失败时要显示的说明。

如果漏写导入，在测试模块里只写 `gcd(54, 24)`，会得到找不到函数名的 E0425。私有项**可以访问**和名字**已经在作用域中**是两回事；除了导入，也可以直接写 `super::gcd(54, 24)`。

测试输出类似下面这样。前一部分是库的单元测试；虽然这里没有文档示例，仍会看到单独的 `Doc-tests` 段：

```text
running 2 tests
test tests::common_divisor ... ok
test tests::with_zero ... ok

test result: ok. 2 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out

   Doc-tests gcd

running 0 tests

test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out
```

`#[cfg]` 也能用来按平台或功能开关选择代码，可用 `any(...)`、`all(...)`、`not(...)` 组合条件。例如在 `Cargo.toml` 中声明：

```toml
[features]
default = []
extra = []
```

再把 `#[cfg(feature = "extra")]` 放在某个项前，用 `cargo build --features extra` 启用。平台条件也可以写成一个完整的声明：

```rust
#[cfg(any(unix, windows))]
pub fn supported_platform() -> bool {
    true
}

#[cfg(all(unix, target_pointer_width = "32"))]
pub fn unix_32_bit() {}

#[cfg(not(feature = "extra"))]
pub fn fallback() {}
```

在 `default` 列表中可以写入要默认启用的特性。这里列表为空，只有主动启用 `extra` 时才切换到相应实现。普通的 `cargo build` 不会打开 `cfg(test)`，与这些包特性是两套开关。

有时需要验证的不是返回了什么，而是调用是否按约定 panic。原书以“不接受零的最大公约数接口”为例。上面的 `gcd` 已支持零，另写包装函数，避免悄悄改变它的行为：

```rust
fn gcd(mut a: u64, mut b: u64) -> u64 {
    while b != 0 {
        (a, b) = (b, a % b);
    }
    a
}

fn gcd_nonzero(a: u64, b: u64) -> u64 {
    assert!(a != 0 && b != 0, "参数不能为零");
    gcd(a, b)
}

#[cfg(test)]
mod tests {
    use super::gcd_nonzero;

    #[test]
    #[should_panic(expected = "参数不能为零")]
    fn reject_zero() {
        gcd_nonzero(10, 0);
    }
}
```

用 `expected` 匹配提示语中的子串，以免无关的 panic 让测试意外通过。这里的片段是独立的例子；要并入已有的 `lib.rs`，只添加包装函数，并把用例移到原有的 `tests` 模块。

测试模块本身只是普通模块。如果同一个源码文件中的测试太多，也可拆到独立文件，再在父模块用 `#[cfg(test)] mod tests;` 接入。对于暂时不想默认运行的用例，可以加 `#[ignore]`。例如，在已有的 `gcd` 项目中加一个遍历更多输入的独立测试文件：

```rust,cargo=gcd,no_run
#[test]
#[ignore = "遍历大量输入，按需运行"]
fn slower_check() {
    for value in 1_u64..10_000 {
        assert_eq!(gcd::gcd(value, 2 * value), value);
    }
}
```

保存为 `tests/slower.rs`。忽略的用例仍要能够编译；下面的「控制测试的行为」一节介绍怎样运行它。

### 基准测试

内置的 `#[bench]` 和 `test::Bencher` 仍需 Nightly，特性门槛为 `#![feature(test)]`。把下面保存为 `benches/gcd.rs`（依赖上面的 `gcd` 库），再运行 `cargo +nightly bench`：

```rust:{channel:"nightly",edition:"2024"}
#![feature(test)]

extern crate test;

use gcd::gcd;
use std::hint::black_box;
use test::Bencher;

#[bench]
fn big_num(b: &mut Bencher) {
    b.iter(|| gcd(black_box(12345), black_box(67890)));
}
```

稳定版可以用 [Criterion](https://crates.io/crates/criterion) 之类的独立基准框架，给对应的 `[[bench]]` 目标设置 `harness = false`，再用 `cargo bench` 运行。

测试结果里的 `measured` 表示测量了多少个基准项目，不是功能测试的通过数。上面的 `iter` 会反复运行待测计算；`black_box` 让编译器不能轻易把固定输入的计算折叠成一个常量。

## 35.2.1 控制测试的行为

默认并行运行测试，并捕获成功测试的输出。`--` 之前是 Cargo 的参数，之后是测试程序的参数：

| 命令 | 用途 |
| --- | --- |
| `cargo test common_divisor` | 按测试名过滤 |
| `cargo test -- --test-threads=1` | 串行运行，便于排查共享状态冲突 |
| `cargo test -- --show-output` | 显示成功测试输出 |
| `cargo test -- --ignored` | 只运行标了 `#[ignore]` 的测试 |
| `cargo test -- --include-ignored` | 运行所有测试，包括被忽略的测试 |

结果中的 `passed`、`failed` 和 `ignored` 分别表示通过、失败和忽略；`filtered out` 表示被名称等条件过滤掉。遇到失败时 Cargo 默认可能不运行后续测试目标，用 `cargo test --no-fail-fast` 可继续运行其余目标。

## 35.2.2 集成测试

每个自动发现的集成测试目标独立编译；它像外部用户一样调用库的公开 API。二进制也可以集成测试：把可复用逻辑放进库，或者用 `std::process::Command` 启动 Cargo 提供的二进制路径（例如宏 `env!("CARGO_BIN_EXE_app")`）。

以下布局复用单元测试一节的 `gcd` 库：

```text
gcd/
├── Cargo.toml
├── src/
│   └── lib.rs
└── tests/
    ├── common/
    │   └── mod.rs
    └── integration_test.rs
```

`tests/` 顶层的 `.rs` 文件会被自动发现为独立的测试目标。把共享代码放进 `tests/common/mod.rs`，避免顶层 `tests/common.rs` 被当作单独的测试目标。在用到它的测试目标里写 `mod common;` 即可。

`tests/common/mod.rs`：

```rust
pub fn sample() -> (u64, u64) {
    (54, 24)
}
```

`tests/integration_test.rs`（必须在上述 Cargo 项目中与 `common/mod.rs` 一起编译）：

```rust,cargo=gcd,no_run
mod common;

#[test]
fn uses_public_api() {
    let (a, b) = common::sample();
    assert_eq!(gcd::gcd(a, b), 6);
}
```

只运行这个测试目标：

```bash
cargo test --test integration_test
```
